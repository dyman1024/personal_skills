# 技术方案设计

## 核心原则

- 以读者正确理解和作出决策为目标。优先保证准确、低歧义、可验证和可执行，不追求华丽表达。
- 使用“总—分—总”结构。先给结论和共同心智模型，再展开实现，最后收束为落地路径和未决事项。
- 坚持“图先于细节”。让读者仅阅读核心图和图后结论，就能理解主要设计思路。
- 使用受控术语和受控句式。一个概念只使用一个正式名称，一个句子只表达一个主要信息。
- 先描述跨平台、跨实现的通用设计，再补充 Android、iOS、Web、PC 或服务端差异。
- 只写有证据的现状和关系。将事实、推断、决定、假设和待确认项清楚分开，不得编造链接、负责人、排期、接口或测试结果。
- 根据方案复杂度裁剪章节。不要堆砌空章节、无信息量图表、重复总结或通用套话。
- 产出物是讲解已有系统的分享页或 wiki 页面（HTML、手绘 SVG 原理图）而不是新方案时，改用 `tech-share-page`。

## 工作流程

### 1. 建立事实与术语基础

1. 阅读用户提供的背景、链接、现有方案、目标载体和约束。
2. 在代码仓库中工作时，先阅读适用的项目说明、模块文档和当前实现；区分“已实现现状”与“目标设计”。
3. 提取并显式记录：
   - 目标读者、阅读任务和预期决策
   - 目标与非目标
   - 范围、约束和关键假设
   - 已确认事实、基于事实的推断、待确认问题和相关文档
4. 建立必要的术语表，统一代码、接口、图和正文中的名称。存在三个以上领域概念、缩写或易混名称时，在文档中提供术语表；否则在写作过程中内部维护即可。

| 正式名称 | 定义与边界 | 不应混用的名称 | 来源 |
| --- | --- | --- | --- |
|  |  |  |  |

5. 只有缺失信息会实质改变核心架构、安全边界、数据正确性或不可逆操作时才阻塞提问；否则采用最小合理假设继续，并明确标记“假设”或 `TBD`。

### 2. 搭建总—分—总骨架

默认使用以下结构，并删除不适用的小节：

```markdown
# <技术方案名称>

## 1. 方案概述
### 1.1 目的与背景
### 1.2 范围与非目标
### 1.3 约束、假设与待确认项
### 1.4 相关文档与术语（按需添加）
### 1.5 方案结论摘要

## 2. 核心设计总览
### 2.1 总体架构
### 2.2 核心流程
### 2.3 核心类或模块关系
### 2.4 外部关系（按条件添加）

## 3. 详细设计
### 3.1 <职责或能力一>
### 3.2 <职责或能力二>
### 3.3 跨端共性与平台差异
### 3.4 可靠性、安全、可观测性与测试（按需拆分）

## 4. 落地节奏与依赖
### 4.1 分阶段计划
### 4.2 依赖与关键路径
### 4.3 风险、灰度、回滚和验收

## 5. 总结与未决事项
```

在“方案结论摘要”中直接说明选用什么方案、核心机制是什么、为什么适合当前约束以及主要代价。不要让读者读完整篇后才知道结论。

### 3. 使用受控技术表达

先识别内容类型，再使用对应写法：

| 内容类型 | 写作目的 | 规则 |
| --- | --- | --- |
| 描述 | 说明系统、关系、状态和约束 | 先写总体关系，再写组成、职责、边界和依据；将现状与目标设计分开 |
| 程序 | 说明操作、调用或状态变化 | 一个编号步骤只写一个主要动作；写明主体、对象、条件和结果；分开正常与异常路径 |
| 决策 | 说明技术选择和取舍 | 使用“决定—理由—代价”；按相同维度比较候选方案；给出明确结论 |

全文遵守以下规则：

- 一个概念只使用一个正式名称。不要为避免重复而切换同义词。
- 一个术语在同一文档中只表达一个含义。首次使用缩写时给出全称。
- 使用与代码、接口、数据结构和图一致的名称。少用可能有多个指代对象的“它”“其”“该模块”或“相关系统”。
- 一个句子只表达一个主要事实、决定、动作或因果关系。句子包含多个并列动作、多重条件或多层转折时，拆成句子或纵向列表。
- 优先使用主动语态并明确动作主体。只有主体未知、不重要或刻意隐藏时才使用被动语态。
- 将条件写在受该条件约束的动作或结果之前。不要省略理解所需的主体、对象、单位和前置条件。
- 一个段落只讨论一个主题。复杂枚举、分支、约束和差异使用列表或表格。
- 用数值、阈值、触发条件、时间范围或验收方法替代“适当”“尽量”“较快”“较高”“必要时”“一般情况下”等不可验证表达。
- 只有证据支持因果关系时才使用“因此”“导致”“保证”“解决”等强因果词。
- 优先使用短句，但不机械限制中文字数。不得为了缩短句子删除必要的技术含义。

### 4. 用关键图建立心智模型

默认使用 Mermaid；目标载体不支持 Mermaid 时，改用其原生图表能力或等价文本图。按语义选图：

| 图 | 使用要求 | 应回答的问题 |
| --- | --- | --- |
| 总体架构图 | 原则上必需；极简单点改动可省略并说明原因 | 系统由什么组成，边界、分层、职责和主数据流是什么 |
| 核心流程图 | 存在运行时流程、状态变化或跨组件交互时必需 | 一次关键操作如何完成，正常与关键异常路径是什么 |
| 核心类或模块关系图 | 存在类、模块、数据模型或核心抽象设计时必需 | 核心对象如何组合、依赖、继承或协作 |
| 外部关系图 | 涉及服务端、第三方、云资源、系统能力或跨团队服务时必需 | 外部参与方、调用方向、协议、信任边界和归属是什么 |
| 依赖关系图 | 三个及以上工作流、组件或团队形成非线性依赖时使用 | 哪些工作可并行，关键路径和阻塞点是什么 |

- 用 `flowchart` 表达架构、边界、依赖和分支流程。
- 用 `sequenceDiagram` 表达有明确时间顺序的跨组件调用。
- 用 `stateDiagram-v2` 表达状态机和生命周期。
- 用 `classDiagram` 表达稳定的类、接口、实体或模块关系；不要为了满足形式虚构类。

每张图都必须：

1. 在图前用一句话说明阅读目的。
2. 使用术语表中的业务或领域名称，避免 `A`、`B`、`Manager1` 等无意义名称。
3. 给关键箭头标注动作、协议或数据。
4. 保持单一抽象层级；单图优先控制在 5–12 个核心节点，过密时拆图。
5. 清楚标出客户端、服务端、第三方、持久化或信任边界。
6. 在图后列出 2–5 条“图中结论”，说明关键决定、理由和约束。
7. 与正文、接口、状态、数据流和实际实现保持一致。

不要用大段文字重复图中的全部连线。正文解释为什么这样设计，以及图中不易表达的约束。

### 5. 展开详细设计

按职责、领域能力或关键流程拆分内容，不要按文件列表机械展开。只保留与当前方案有关的维度。每个重要设计点按需回答：

- 解决什么问题，输入、输出和责任边界是什么。
- 核心接口、数据结构、协议、状态和持久化方式是什么。
- 正常路径与异常路径如何处理。
- 并发、幂等、重试、超时、降级和恢复策略是什么。
- 安全、权限、隐私和信任边界是什么。
- 性能、容量、资源和成本约束是什么；如何测量和验收。
- 日志、指标、追踪和告警如何支撑排障。
- 兼容、迁移、灰度和回滚如何完成。
- 如何测试和验收，关键失败模式是否被覆盖。
- 采用了哪些关键取舍，未选方案为什么不适合当前约束。

对重要决定使用“决定—理由—代价”结构。对尚无数据支撑的目标写明测量方法或标记 `TBD`，不要把期望写成事实。

### 6. 处理跨端共性与差异

先统一描述领域模型、协议、状态机、核心流程、错误语义和安全约束。再在相关实现点后补充平台差异，不要分别复制多套相同方案。

涉及两个及以上平台且存在差异时，优先使用差异表：

| 维度 | 通用约束 | Android | iOS | Web | PC |
| --- | --- | --- | --- | --- | --- |
| <生命周期、存储、网络、权限、UI 集成或发布等> | <共同语义> | <差异> | <差异> | <差异> | <差异> |

删除不涉及的平台列。只有平台差异会改变架构或主流程时，才为该平台增加独立图。

### 7. 收束落地节奏与依赖

落地计划至少包含：

| 阶段 | 目标与范围 | 主要交付物 | 前置依赖 | 完成/验收标准 | 风险与回滚 |
| --- | --- | --- | --- | --- | --- |
| Phase 1 |  |  |  |  |  |

同时明确：

- 关键路径、可并行工作和阻塞依赖
- 跨团队、跨服务、数据、接口、基础设施或发布依赖
- 每阶段的可验证出口，而不只是任务列表
- 灰度顺序、兼容窗口、回滚边界和风险控制
- 已知负责人和时间；未知时使用 `TBD`，不得推测

如果依赖关系非线性，增加依赖关系图。最后重申方案目标、核心设计、关键路径、最大风险和仍待决定的事项；不要机械复述正文。

### 8. 分两遍复核

1. 先做语义复核：检查技术含义、事实依据、边界、异常、代价和落地路径是否完整。
2. 再做表达复核：检查术语、句子、段落、图文和可验证性；直接修订发现的问题。

不要用语言简化掩盖技术缺口。语言检查工具或 LLM 自检只能辅助，不能替代技术判断和证据核验。

## 质量门禁

交付前逐项检查：

- [ ] 已明确目标读者、目的、范围、非目标、约束和方案结论摘要。
- [ ] 事实、推断、决定、假设和待确认项边界清楚，没有编造事实或链接。
- [ ] 一个概念只使用一个正式名称；缩写、接口、图和正文术语一致。
- [ ] 一个句子只表达一个主要信息；动作主体明确，条件位于动作或结果之前。
- [ ] 模糊形容词已替换为阈值、条件、观察方法或验收标准。
- [ ] 文档符合“总—分—总”，一个段落只讲一个主题，结尾不是机械重复。
- [ ] 关键图足以建立主要心智模型；图、正文、接口、状态和数据流一致。
- [ ] 架构图、流程图、类或模块关系图及外部关系图已按适用性提供；省略时有合理原因。
- [ ] 跨端内容先讲共性，再讲平台差异，没有复制多套相同方案。
- [ ] 关键决定包含理由和代价；候选方案使用相同维度比较并给出结论。
- [ ] 正常、异常、超时、重试、降级和恢复路径已按适用性说明。
- [ ] 落地计划包含阶段、依赖、关键路径、验收、风险、灰度和回滚。
- [ ] 读者能据此作出决策、实施方案并验证完成结果。
