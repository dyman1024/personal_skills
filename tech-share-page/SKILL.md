# 技术分享页（图解）

产出一份能直接投屏讲解、也能长期当 wiki 读的 HTML 页面。读者看完总图和每节的图，就能说清系统由什么组成、一次调用怎么走、每个子模块怎么工作。

## 核心原则

- **图是主体，文字解释图。** 每个子模块至少一张原理图。正文只写图里不好表达的原因、约束和数字。
- **总—分结构。** “总”用一张模块总图建立全局心智模型，“分”逐个讲子模块。不要把总图拆散到各节。
- **默认只讲当前设计。** 背景、历史、“改造前后”对比、交付时间线、验证清单都不写，除非用户要求。有“为什么”时，用一句原理或图注说明。
- **以代码为准。** 方案、PR 描述和会话记录是线索，最终事实以最新主干代码、合约和常量为准。方案与实现不一致时写实现，必要时注明差异。
- **只写有证据的内容。** 数字（阈值、超时、行数、个数）从代码或工具重新算一遍再写。不确定的标“未验证”，不编造。
- **一致的视觉语言。** 颜色只表达语义：浅蓝 = 关口和主路径，浅红 = 拒绝，浅黄 = 等待或需确认，浅绿 = 放行。其他元素用黑、灰、白。

## 工作流程

### 1. 明确用途

确认或合理假设以下几点，不清楚且会改变结构时才提问：

- 读者和场合：内部分享（投屏、多长时间）、wiki（长期查阅）还是新人入门。
- 范围：哪些模块要讲，哪些不讲。
- 交付位置：Artifact 页面（默认）、仓库里的文档目录，或用户指定的 wiki。
- 语言：跟随用户；中文时按受控中文写（见第 6 步）。

### 2. 收集材料，再用代码核实

按这个顺序收集，记下每条事实的来源：

1. 用户点名的会话、文档、截图。
2. 相关会话：列出近期会话，按关键词搜索会话记录，找到设计讨论、负责人决定和验证结果。
3. PR 和卡片：用 `gh pr view <n> --json title,body,mergedAt,additions,deletions` 和 `gh issue view` 读正文，保存到草稿目录再读，不要一次性塞进上下文。
4. 设计稿、规格、ADR、项目记忆。
5. 拉取最新主干（例如 `git fetch origin <branch>`），读真正的实现：合约和枚举、检查顺序、常量、状态机、协议握手、清单文件。用 `git grep` 定位，读关键段落。

产出一张内部“事实表”：模块 → 关键类或文件 → 关键常量和数字 → 来源。后面的图和文字只用这张表里的事实。

### 3. 拆出总图和子模块

1. 找出 4–8 个核心子模块。每个子模块要能用一句“原理”讲清楚。给它们编号 ①②③…，编号贯穿总图、模块卡片和各节标题。
2. 设计总图：分层带（例如 Agent 层 / 服务端 / 通道 / 客户端），客户端按进程或执行身份分区；如果用户参与流程，在左侧画“用户”列，标出用户直接参与的动作。在总图上用圈号标出每个子模块的位置。
3. 再选一张“一次调用的路径”泳道图，把子模块串成一条时间线。
4. 为每个子模块从图谱里选 2–3 张图（见 [references/svg-diagrams.md](references/svg-diagrams.md)）。

### 4. 搭页面

从 [assets/template.html](assets/template.html) 开始，它已经带好配色、字体、组件和图的样式类。页面结构固定为：

1. **页头**：一行眼眉、标题、一句导语、事实行（卡片、PR 数和行数、代码基线）、目录、建议讲法（各节分钟数）。
2. **总**：一段三层关系说明 → 模块总图（图注以“读图顺序”开头）→ 子模块卡片网格（链接到各节）→ 3–5 条贯穿全篇的规则 → 一次调用的路径图。
3. **分**（每个子模块一节）：标签行（编号、PR、关键代码路径）→ 带编号的标题 → 一段“原理” → 2–3 张图（每张有图注）→ 必要时一张紧凑表格或两栏面板。
4. **附录**：合约和发布要求、已知限制、代码与 PR 索引。

视觉规范见 [references/visual-system.md](references/visual-system.md)。

### 5. 画图

按 [references/svg-diagrams.md](references/svg-diagrams.md) 手写内联 SVG。最容易出错的四条：

- **连线最后画。** SVG 按书写顺序绘制，先画的连线会被后画的背景区或方框盖住。连线写在它穿过的所有区域和方框之后。
- **汇聚和分发用总线。** 多个来源汇入一个目标时，画短横线 → 竖总线 → 一个箭头；不要画多条斜线、只有最后一条带箭头。
- **每张图用自己的 marker id 前缀**，例如 `o1m`、`p2a`，避免页面内重名。
- **文字留足空间。** 估算宽度：中文 1.0 em，拉丁字母约 0.56 em，等宽 0.6 em；文字离框边至少 12 px，离连线至少 6 px。

每张图包在 `<figure>` 里，`<figcaption>` 第一句加粗写结论；`<svg>` 带 `role="img"` 和同样内容的 `aria-label`。

### 6. 写文字

- 一个概念只用一个名称，和代码、合约、图里的名称一致；代码标识符用 `code` 样式。
- 一句话只说一件事：一个事实、一个决定或一个因果。条件写在结果前面。
- 用数字和阈值代替“较快”“必要时”这类词，带上单位。
- 原理段落写“它怎么工作、为什么这样排”，不要复述图里的每条线。
- 中文里不混用同义词，不写套话，不用“值得注意”“总的来说”。
- 如果环境里有 `technical-research-explainer` 的受控写作指南，按它区分事实、推断和未知。

### 7. 自检

1. 运行检查脚本，修到没有 error，再逐条判断 warning：

   ```bash
   python3 scripts/svg_lint.py <page.html>
   ```

   它检查：SVG 能否解析、marker id 是否重名、连线是否被后画的形状盖住、文字是否超出 viewBox 或所在方框、实线是否停在形状边上却没有箭头、文字是否压线或互相重叠。宽度是估算值，贴边 1–3 px 的提示要结合截图判断。
2. 可行时看一次渲染效果。本地 `file://` 页面在部分环境里无法截图：在页面目录起本地服务（`python3 -m http.server <port> --bind 127.0.0.1`），另存一份在开头加了 `<meta charset="utf-8">` 的预览副本（Artifact 发布时才会补字符集，本地文件没有），用浏览器打开预览副本截图。只看一次，看完删掉预览副本、停掉服务。
3. 对照事实表复核每个数字、名称和检查顺序。

### 8. 交付

- 默认发布为 Artifact，给出链接，并提醒页面默认私有，分享前要在 Share 菜单里打开。
- 用户要放进仓库或 wiki 时，按目标位置的规则保存（例如仓库的文档规则、是否允许提交 HTML）。
- 在回复里说明：页面结构、哪些内容没写（按“默认只讲当前设计”省略的部分）、哪些地方没有验证（例如没看到渲染效果）。
- 用户指出图的问题时，修改后再跑一遍检查脚本，再发布到同一个链接。

## 质量门禁

- [ ] 页面是“总—分”结构：总图在前，子模块编号在总图、卡片和标题里一致。
- [ ] 每个子模块有一段原理和至少一张原理图；没有空章节。
- [ ] 默认没有背景、历史、前后对比、交付时间线；用户要求的除外。
- [ ] 每个数字、名称、顺序都能在事实表里找到来源，主干代码已核实。
- [ ] 颜色只表达语义；页面是白底、黑字、灰字、浅蓝强调。
- [ ] 每张图有图注和 `aria-label`，连线有标注或在图注里解释。
- [ ] `svg_lint.py` 没有 error；剩余 warning 已逐条确认。
- [ ] 回复里列出了未验证项和交付位置。
